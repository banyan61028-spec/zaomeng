# 04 · 前端架构与改造指南

> 目标：**保留后端不动，整体重写/改造前端**。本文说明现有前端的结构、与后端的对接方式，以及重写时的关键注意点。

## 1. 技术栈

Next.js 16.3（App Router）+ React 19 + TypeScript + Tailwind CSS 4 + `lucide-react` + `clsx`/`tailwind-merge`。

依赖见 `frontend/package.json`，脚本：`dev` / `build` / `start` / `lint`。

## 4. 与后端的对接层（重写时最关键）

### 4.1 API 客户端 `lib/workflowApi.ts`

这是**现成的前后端契约**，重写前端时可直接复用或严格对齐。核心函数：

| 函数 | 对应接口 |
|---|---|
| `startProject(params)` | POST /api/project/start |
| `executeStage(id, stage, data, signal)` | POST /execute/{stage}（SSE，**直连后端**） |
| `intervene(id, stage, mods)` | POST /intervene（SSE，**直连后端**） |
| `continueWorkflow(id)` | POST /continue |
| `stopProject(id)` | POST /stop |
| `getProjectStatus(id)` | GET /status |
| `getArtifact(id, stage)` | GET /artifact/{stage} |
| `saveSelections(id, stage, sel)` | PATCH /artifact/{stage} |
| `updateModels(id, models)` | PATCH /models |
| `uploadArtifactImage(...)` | POST /artifact/{stage}/upload_image |
| `fetchStages()` / `fetchSessions()` | GET /stages / /sessions |
| `startStandardPipeline/startActionTransfer/startDigitalHuman` | 各 Pipeline 创建 |
| `fetchPipelineTasks/fetchPipelineTask/deletePipelineTask` | /api/tasks |
| `subscribePipelineTask(id, onEvent)` | GET /tasks/{id}/events（SSE） |
| `fetchSandboxTasks()` | GET /sandbox/tasks |
| `fetchApiModels(...)` | GET /api/models |
| `fetchStandardTemplates()` | GET /pipelines/standard/templates |
| `uploadMedia/uploadFile` | 上传 |
| `clearTempCache()` | DELETE /cache/temp |
| `parseStreamEvents(response)` | 解析 SSE 流为 AsyncGenerator<StreamEvent> |
| `deleteSession(id)` | DELETE /sessions/{id} |

### 4.2 代理配置 `next.config.ts`

Next.js 用 `rewrites()` 把 `/api/*`、`/code/*` 代理到后端 `BACKEND_API_URL`（默认 `http://127.0.0.1:8000`）。

⚠️ **重要**：SSE 流式接口（`/api/project/{id}/execute/{stage}`、`/intervene`、`/api/tasks/{id}/events`）**不能走代理**（Next 代理会缓冲整个响应，破坏 SSE）。所以 `workflowApi.ts` 里这些请求用 `STREAM_API_BASE`（`NEXT_PUBLIC_API_URL` 或默认 `http://127.0.0.1:8000`）直连后端。

### 4.3 模型选择 `lib/modelRegistry.ts` + `config/models.ts`

- `config/models.ts`：前端常量——`STYLES`（8 种风格）、`VIDEO_RATIOS`、`VIDEO_RESOLUTIONS`、`VIDEO_GENERATION_MODES`（三种视频模式及其 `ability`/`modelKey` 映射）、`videoModeAbility()`/`videoModeModelKey()`。
- `lib/modelRegistry.ts`：`fetchModelGroupsByType(type)` / `fetchVideoModelGroupsByAbility(ability)` 按 provider 分组，供模型下拉框用。

## 5. 主流程交互时序（前端必须实现）

```
1. 用户填创意/风格/模型 → startProject() → 拿 session_id
2. executeStage(id, "script_generation")，用 parseStreamEvents 读进度
3. 收到 stage_complete → getArtifact(id, "script_generation") → 渲染 ScriptStage
4. 用户确认/修改 → saveSelections() 或 intervene() → continueWorkflow(id)
5. 循环 2-4 依次走完 6 阶段
6. post_production 完成后展示 final_videos
```

状态轮询：`getProjectStatus(id)` 返回每阶段 `status` 映射，`waiting`/`completed` 驱动停点 UI。AppShell 每 3s 轮询 `/api/sessions`、`/api/tasks`、`/api/sandbox/tasks` 更新侧栏任务列表。

## 6. 重写前端建议

1. **后端契约已冻结**：直接复用 `lib/workflowApi.ts` 的所有函数签名，重写 UI 层即可，几乎零后端改动。
2. **保留路由结构**：`/`（主流程）、`/sandbox`、`/pipelines/{3}`、`/settings` 是导航与侧栏任务跳转依赖的路径。
3. **产物渲染**：所有图片/视频路径都是相对 `code/` 的（如 `result/image/<session>/xxx.jpg`），用 `<img src={`/code/${path}`}>` 访问；`selected` 为空表示待选。
4. **停点逻辑**：`waiting` = 需用户确认/选择；`completed` = 可 continue。不要在前端自动 continue。
5. **SSE 直连**：`execute`/`intervene`/任务事件流必须直连 `127.0.0.1:8000`，不能走代理。
6. **设计系统**：当前是 `xyq-*` 前缀 + 蓝色 accent + `gray-50` 画布（Tailwind 4，`globals.css` 定义 token）。改造视觉只需动 `globals.css` 与组件 className，无需改逻辑。
